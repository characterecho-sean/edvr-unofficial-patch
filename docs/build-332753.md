# Game build 332753 (4.4.1.0)

Elite Dangerous: Odyssey updated on 2026-09-02 from build 330683 (4.4.0.3) to
build 332753 (4.4.1.0). This is the record of what EDVR was re-checked against
on the new build, what moved, and what was left unproven.

Every fix in EDVR finds its target by what that target does or looks like, so
most of them do not care which build compiled the game. A handful do care, and
this is the list of those, one row per thing that could have moved. The rule
for `kVerifiedBuilds` in `src/common/proxy.cpp` has not changed: **adding a
build to it is a claim that someone re-ran the capture and confirmed the
hashes, not that it probably still works.**

---

## The short version

**One thing moved: the camera marker, and the finder has named its replacement.** `d3d11.camera_index_type_offset`
(`0x4D71C50`) is an address inside one build of the executable, and 332753 put
something else there. Everything else measured so far held. The
resolution patch still finds six call sites, the exposure fix still detects the
same compute shader, the plume replacement still matches its vertex shader, the
scene block still holds the view matrix where it did, and the glare train still
matches on shape.

### The camera marker, and what was done about it

The failure is unambiguous and it is not intermittent. On 330683 the scan
succeeded in session after session — one, two and three identifications in the
last three logs before the update, with no failures. On 332753 it fails every
attempt, four attempts a session, over eleven to fifteen gigabytes each time:

```
camera view: no records of that type found over 11787 MB. Most likely the game
updated and d3d11.camera_index_type_offset (0x4D71C50) no longer points at the
right thing.
```

The fix then does what it was built to do. It reports "do not know" rather than
a number, falls back to counting keypresses, and Explorer Cam keeps working with
the caveat the log already prints: a missed press desynchronises it until you
leave the camera and come back.

Re-deriving the value at the desk is not possible. The old executable is gone —
the update overwrote it in both installs — and the new one is RTTI-stripped
(nineteen class-name strings in a hundred-megabyte binary, none of them a
camera), so there is no name to follow from the old address to the new one.

So `d3d11.camera_index_find` was added instead. It looks for the array rather
than the marker: an array of one polymorphic type is, from outside, a stretch of
memory where the same pointer into the game's image reappears at a fixed stride,
and the stride is already known. It prints each candidate as the offset it would
have to be and adopts none of them — the number goes into the ini by hand, and
the behavioural identification already in the file is what confirms or refuses
it. It is off unless armed, runs only after the ordinary search has failed, and
runs once a session.

**It is unflown.** It needs one session on 332753 with the key set.

Four of the checks the update prompted turned out not to be checks at all. They
are written up under [what could not move](#four-things-that-cannot-move)
because a check nobody can fail is worth knowing about before the next update
sends someone looking for it.

## Evidence and where it came from

No build of `main` has been flown on 332753, and it turns out none needs to be.

Three branches had a build installed on a 332753 rig within twenty minutes of
each other: `main`, `claude/headlook-functionality-9bada8` (the head-anchor
arc, in the Frontier install) and `claude/openxr-toolkit-perf-port-jtd2rc` (the
render-scale arc, in the Steam install). **Every file that carries a pinned
constant or a schema offset is byte-identical across all three** —
`fss_dump.cpp`, `fss_panel.cpp`, `fss_ring.cpp`, `fss_probe.cpp`,
`fss_reveal.cpp`, `particle_fix.cpp`, `sunglare_vs.h`, `sunglare_fix.cpp`,
`vscreen_res.cpp`, `glitch_frame.cpp`, `camera_view.cpp`. `vscreen.cpp` does
differ between them, but not on any line that touches the FSS hash gates, the
witchspace skip, the panel rect or the heal.

The code doing the matching is the same code, so what any of those builds
reports about the game is evidence about the game. **That is the method worth
keeping for the next update: you do not need a dedicated build to re-verify
what is keyed to a game version, only a build whose matching code you have
diffed.**

Two short sessions exist so far, and they agree with each other line for line:

| | Frontier install | Steam install |
|---|---|---|
| Session | 2026-09-02 05:56 | 2026-09-02 05:50 |
| Build | `318c827-dirty` (head anchor) | `f9f47f9` (render scale) |
| Resolution sites | 6 | 6 |
| Exposure shader | `F1FB2EEFB662F3AA` | `F1FB2EEFB662F3AA` |
| Plume vs | `EB787F983BC1F5A3` | `EB787F983BC1F5A3` |
| Glare train | `variant 1 COMPILED` | `variant 1 COMPILED` |
| View matrix | offset 932, rows 1.000 | offset 932, rows 1.000 |

Both sessions end about thirty seconds after the game finishes loading, which
is why the rows below are still open: nobody flew, scanned, or jumped. Neither
is a `-dirty` tree worth worrying about for the Frontier one, since the Steam
build was clean and reported the same six things.

### One piece of corroboration for the 5376-byte block

The head-anchor arc, working the same day on the same game build, measured the
camera rig's position at **float 1100 of a 5376-byte block** on the head draw,
and found it following the walking commander on preset 2. That is the same
offset in the same-sized block that the transition flash detector watches, which
is good reason to expect the schema did not shift.

It is corroboration and not the check. The detector's own certification is the
test, because what it has to establish is not where the value sits but that the
value *moves like a camera* over 300 frames. That row stays open until it says
so itself.

### A note for whoever installs next

Two game directories carry EDVR on this rig, and other arcs fly them. An
install placed over another arc's pair is one problem; the sharper one is that
**a reinstall does not undo an `edvr.ini` edit.** The three-way merge reads a
changed value as a user edit and writes it faithfully back into the new
template, inline comment stripped. Diagnostic keys armed for one flight
therefore survive into the next arc's flight, silently. Revert them by value,
and do not trust an install to do it for you.

## What is keyed to the build

### 1. The verified-build list

`src/common/proxy.cpp`, `kVerifiedBuilds[]`. Read by `gameBuildIsVerified()`,
which decides which of two greetings the log opens with, and by
`vscreen_res.cpp` for the sentence it appends to its own report.

Nothing else branches on it. No fix refuses because a build is unfamiliar.

### 2. The startup greeting

`src/d3d11/d3d11_proxy.cpp`. This used to name build 330683 as a literal inside
the log string, which was right for as long as the list had one entry and would
have gone quietly wrong the moment it had two. It now calls
`verifiedBuildList()` and prints whatever the list actually holds, in both
branches. Fixed at the desk, before any flight.

### 3. The two things measured from one build

Named in README's *Game updates* section: the transition flash fix's viewpoint,
and Explorer Cam's camera marker. Both degrade rather than guess, and both say
so in the log.

### 4. The resolution patch

`src/d3d11/vscreen_res.cpp` matches the *shape* of six call sites and accepts
anywhere from three to twelve. It proceeds on an unverified build by design.

### 5. The 5376-byte scene block

Several features read fixed float offsets in a 5376-byte constant buffer: the
camera position at float 1100, the true view matrix at 932. On `main` the
consumers are the transition flash detector (`glitch_frame.cpp`), sun glare's
scene rows (`sunglare_fix.cpp`), the FOV probe (`fov_probe.cpp`) and the
particle substitution's buffer copy (`particle_fix.cpp`).

A schema shift shows up as the flash detector refusing, or as the view-matrix
line failing to appear.

### 6. Pinned shader hashes

A recompiled shader silently stops matching. Every fix that pins one is built
to notice and do nothing — which means **the evidence for a hash is always the
presence of its engage line, never an error.** None of these gates logs a
mismatch. Absence is the failure signal, and absence also looks exactly like
"the player never flew that mode", which is why the flight plan below is
specific about what to do.

### 7. The commander head part list

Sean's ini, not code. **Not on `main`.** See below.

## The complete check: what it found

Two sessions on 2026-09-02, both on `main`'s build (`da50d68`, DLL hashes
verified against `build\` before the flight), 06:47 and 07:06. Everything that
could be reached was reached, and everything that engaged said so.

| Check | Result |
|---|---|
| Transition flash | **ACTIVE both sessions**, at float 1100 of the 5376-byte buffer; 274 and 229 of the first 300 frames moved |
| Resolution patch | 6 sites, applied |
| Exposure | `F1FB2EEFB662F3AA` confirmed once per eye |
| Sun glare | `variant 1 COMPILED` |
| Smoke plume | replacement compiled, `EB787F983BC1F5A3` |
| Solar flare | replacement compiled, `6041FD2D3D0164E1` |
| Witchspace starfield | `9AEC596A2B036EA6`, 431,232 draws withheld |
| FSS composite | reveal engaged in both mechanisms, `953C8123AD8DC13B` |
| FSS colour / prepass | panel rect resolved a 4-quad screen family |
| FSS ring family | ring engaged, quad and mesh, all three hashes |
| FSS heal | engaged, left eye filled from the right |
| FSS resolution | body layer created at full eye resolution |

**The transition flash was never faulty.** It certified in both sessions and
neither disabled itself. The first session withheld 129 frames over eighteen
minutes and recognised 3,533 more as render-pass geometry, which is the detector
learning the scene rather than misfiring; the second withheld 35 over eight. A
detector that has not yet learned a repeating jump size withholds more early in
a session than late, so the first minutes of any session are its worst, and a
restart lands you in a different scene rather than fixing anything.

### The eye-series instrument did not deliver

`fss_eye_series` armed, compiled its shader and captured, but wrote no files and
printed no dispatch hashes. It said once, seventy milliseconds in, that no
submitted texture had been published for eye 0 — which is the openvr half not
being up yet that early — and never spoke again. That leaves the tonemap and
accumulate hashes unproven; reaching those needs `fss_eye_dump`, which costs
about 700 MB and one visible hitch. They are diagnostic-only, read by no shipped
fix, so the row stays open rather than blocking anything.

### The camera marker's replacement

The finder ran in both sessions and offered three qualifying candidates each
time. Only one is the same in both:

| Offset | Session 1 | Session 2 |
|---|---|---|
| `0x4DDEFB0` | 19 slots, ordinal 11 reads 3 | 19 slots, ordinal 11 reads 3 |
| `0x55D9240` | 40 slots, reads 0 | 40 slots, reads 0 |
| `0x5129468` | 64 slots, reads 0 | 64 slots, reads 1003834635 |
| `0x4DDBC58` | 64 slots, reads 256 | 64 slots, reads 0 |

`0x4DDEFB0` is the answer if any of them is. It is identical across two
sessions in a freshly laid-out heap, it reads a plausible view both times, and
**its run is exactly 19 slots — the length 6ad.8a measured the camera settings
array at on the old build.** The other two stable-looking candidates read 0,
which is the least discriminating value an integer can hold.

It is a candidate and not yet an answer. Set it, relaunch, cycle a preset or two
in Explorer Cam, and the behavioural identification says whether it was right:

```
camera_index_type_offset = 0x4DDEFB0
```

The old value was `0x4D71C50`, so the shift is `+0x6D360`.

## Four things that cannot move

These came out of reading the code that the update was supposed to have put at
risk. Each one is a check that cannot fail, which is worth writing down so the
next update does not send anyone hunting for a log line that was never going to
appear.

**`kOutputHash B74273EC13F7CD59` is dead.** `fss_dump.cpp:35` defines it and
nothing reads it — not in that file, not anywhere in the repo. The packed
output dispatch is matched by shape instead (`width >= 3000` and format
`R10G10B10A2_UNORM`), and the comment above the shape test already says why:
the 32-channel probe showed the learned hash never appearing. The constant is a
leftover. There is nothing to re-verify and nothing that can break.

**Sun glare is not gated on a shader hash.** `94D5C556DFD6D705` appears once in
the whole tree, as prose in `sunglare_vs.h`, recording which disassembly the
replacement shader was transcribed from. It is never compared. The glare train
is recognised by shape and by the textures it binds: a six-vertex instanced
draw with a 2048x1024 format-98 sheet on both of the first two pixel-shader
slots. **Those five numbers are what a game update can break, not the hash.**
They held on 332753.

**`glare train shaders: vs=... ps=...` can never print.** It sits behind a flag
that is initialised false and hard-assigned false in the configure path, with a
comment saying the mechanism it belonged to was superseded by the world shader.
Its absence from a log means nothing at all.

**The commander head list is not `main`'s.** `fix.explorer_cam_head`,
`advanced.explorer_cam_head_draw` and the `commander head:` log lines exist
only on `claude/headlook-functionality-9bada8`. Installing `main` over the
head-anchor build carried those keys to the end of their sections with a note,
which is the installer behaving correctly, not a loss. Re-deriving the ten-part
list against 332753 is work for that branch, not this one, and the pre-flight
log shows the ten parts still parsing and being watched — which is as far as
that evidence goes, because that session never entered Explorer Cam.

## If a hash has moved

Re-derive it with the existing tools: the `hotkey.dump_draws` census plus
`tools/diff_draw_census.py`. For the FSS compute shaders there is a better
instrument — `advanced.fss_eye_series` prints
`fss series: scanner dispatch D writes WxH fmt=F ch=<hash>` for eight
dispatches during a scanner frame, which is the observed hash handed to you
directly.

**The geyser rule applies to all of them: a hash earns a replacement only via
its own disassembly, never by likeness.** In 0.12.3 a second hash was granted
the solar flare's shader because it looked like a match, and it turned out to be
the witchspace starfield, which the fix then deleted. Add a new hash
*alongside* the old one so both builds keep working.
