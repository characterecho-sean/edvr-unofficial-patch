## What changed in the game

Elite updated on 2026-10-20 from build 332841 (PE stamp `0x6A989634`, image
size `0x6409000`, SHA-256 `e6be8bbe…`) to build 334473 (`0x6ACD513D`,
`0x640C000`, `6891f70a…`; `VersionInfo.txt` 2026.10.13.334473). Code grew by
`0x2C50` bytes; `.rdata` and `.data` start `0x3000` higher. Both executables
are kept in `analysis/` (`EliteDangerous64.exe` is 332841,
`EliteDangerous64-334473.exe` is 334473), and the Ghidra project
`analysis/ghidra/ED334473` holds the analysed new build.

The update also rewrote 851 content-addressed data files. Of the two effects
archives, `Effects_` is unchanged since 2026-10-01 and `Effects2_` was
rewritten.

## How the move was measured

`tools/build_diff.py map` (added for this update) matches every code unit of
the old executable to the new one: byte-identical units anchor an in-order
walk, and every differing byte run must verify as a rel32, RIP-relative or
image-base displacement that lands on the mapped counterpart of its target.
Data addresses map by cross-reference voting plus a content check; vtables
are checked slot by slot. Of 301,451 old code units, 97% are IDENTICAL or
RELOC-ONLY.

All 87 functions that hold an EDVR-bound address map IDENTICAL (9) or
RELOC-ONLY (78); none changed. A second, independent mapper written for the
patch-note review agreed on every address both covered, and objdump of
named hooks on both sides matches once call and data targets are masked.
Walking callees seven deep from those functions finds one changed function,
`0x4313FC0` → `0x4316C80`, a keyframe step under job `0x4321810` that EDVR
only times.

Pins that had to be recomputed because they cover moved displacements: every
FNV body hash (the Oculus profile's eleven and the kinematic set),
`kUiPanelSiteBytes`, and the call-site pins at `0x42B42EA`, `0x42B4ED1`,
`0x43130A5`, `0x8D5337` and `0x4E70B6`. All 39 hook prologues are
byte-identical at their new addresses.

Terrain cull cover needed nothing: its signature scan finds the one call site
in 334473 on its own (site `0x4458D5D`, builder `0x4441580`).

2026-10-20, an independent cross-check from PR 121 (REA and Ghidra, masked
byte matching; not merged): of its 173 old-to-new addresses, 171 equal
`build_diff.py map`'s. The other two are in a function whose body changed in
334473, which `map` reports CHANGED and does not place; PR 121 places them,
and both fit the neighbouring +0x2D80 shift:

| What | 332841 | 334473 |
|---|---|---|
| planet draw-list builder | `0x4462E80` | `0x4465C00` |
| its call to the record writer `0x44587C0` | `0x4463A83` | `0x4466803` (offset `0xC03`, as before) |

Neither is a runtime constant: `terrain_cull_cover_core.h` cites them in its
derivation comment only, which still gives the 332841 values. The
per-(patch, view) test that comment also cites, `0x445BA40`, is placed by
neither method.

**2026-10-20, VR, a user on the Oculus PC runtime (Frontier launcher install,
v0.20.0), log `edvr_gfx_20261020_222116`: Elite ran on its native Oculus back
end.** The route was installed on a matched profile (`profile=1
installed=1`), but its counters never moved after startup: `calls=4 exact=0
near=0 rejected=0 forwarded=4`. No call naming LibOVR ever reached the hook,
yet `LibOVRRT64_1.dll` was loaded and no `openvr_api.dll` was. The SteamVR
log of the same day reads `exact=0` too, but that rig has no Oculus runtime
for Elite to find.

**It is new with 334473.** The same user's v0.19.1 log on 332841
(`edvr_gfx_20261018_005428`) reads `calls=4 exact=0` at log open, as now,
then about 3 s later `calls=10 exact=2 rejected=2` from caller `0x4E70BC`
and further calls through the session; Elite ran on EDVR's runtime. On
334473 the hook takes no call at all after log open, on two rigs: not the
LibOVR load, and not the other loads that followed it on 332841 (the SteamVR
rig loaded EDVR's runtime without one). The report's call sites are the same
in v0.19.1 and v0.20.0, and the route code differs only by the retarget, so
this is not a logging change. The input gate's import patches, installed
about 30 s after start, still see their calls on 334473 (`XInputGetState
slot 0 is observed`), so the import table is not continuously policed.

**Root cause, found 2026-10-20 (flat flight of `5e5bf8f8`, log
`edvr_gfx_20261020_165535`): EDVR replaces its own route.** The slot holds
EDVR's route at log open, then 2.3 ms later `d3d11.dll+0x2DCA0` for the rest
of the session. That address in EDVR's proxy is `hookedLoadLibraryW`, the
"LoadLibrary deadlock bypass" PR 92 (plugins, first in 0.20.0-rc.3) installs
on the executable's `LoadLibraryA/W/ExA/ExW` at log open: it returns an
already loaded module by name or jumps straight to KERNEL32's `LoadLibraryW`,
never to the route it displaced. So every 0.20.0 build since rc.3 lets
Elite's LibOVR load through, on any game build; 334473 only coincided.

Hypotheses as written before that flight, kept for the record:
H1 something restores Elite's `LoadLibraryW` import slot once, after the
route installs at DllMain and before Elite's VR probe (signature: the slot
reads KERNEL32's `LoadLibraryW` again by log open or soon after); H2 another
module replaces it (signature: the slot points into a third module); H3 the
slot still holds the route's function and Elite's calls go elsewhere
(signature: slot unchanged, counters still flat). No code in either build
takes an import slot's address (`lea` into the IAT: 0 in both), so H1 would
be a generic import walk, not a direct write.

## Ruled out

- ruled out: struct-offset changes in EDVR-bound code, because every bound
  function is IDENTICAL or RELOC-ONLY and RELOC-ONLY keeps immediates and
  displacements.
- ruled out: the light grid cache being affected by the hangar light fix,
  because the cache holds view-derived cluster geometry and its builder,
  refresh, copy and globals are unchanged apart from the move.
- ruled out: 334473 changed how Elite loads LibOVR, because the loader
  (`0x4E6E40`: `SearchPathW`, `GetFullPathNameW`, the signature check at
  `0x4E7D20`, then `LoadLibraryW` at `0x4E71B6`) is relocation-only, it has
  no `GetModuleHandle` short-circuit, the only LibOVR name string is the same
  `LibOVRRT%hs_%d.dll`, and the import table differs only by the +0x3000
  move (`LoadLibraryW` at `0x4DB62E0`, the slot the route hooks).
