## What changed in the game

Elite updated on 2026-10-23 from build 334473 (PE stamp `0x6ACD513D`, SHA-256
`6891f70a…`) to build 334925 (`0x6ADA8048` = 1792704584, SHA-256
`ed5a8f8c…e264b63`; Steam `VersionInfo.txt` 2026.10.23.334925). The image size
is the same, `0x640C000`, and the seven sections keep their virtual addresses.
`.text` shrank by `0x160` (virtual size `0x4DB4AEE` → `0x4DB498E`, raw size
`0x4DB4C00` → `0x4DB4A00`), `.rdata` by `0x20`, `.pdata` by `0x6C`, `.reloc` by
`0x18`; `.data`, `_RDATA` and `.rsrc` are the same size. The three executables
are kept in the main checkout's `analysis/` (`EliteDangerous64.exe` 332841,
`-334473.exe`, `-334925.exe`).

## How the move was measured

`tools/build_diff.py map`, the method `docs/build-334473.md` describes, over
222 distinct addresses: the 213 that the 334473 retarget carried plus the 16
render pipeline seed targets (7 are in both). Result:

| | same RVA | moved | changed | unmapped |
|---|---|---|---|---|
| code, 180 | 1 | 179 | 0 | 0 |
| data, 42 | 19 | 23 | 0 | 0 |

Of the 180 code addresses, 54 are IDENTICAL bytes at the new address and 126
are RELOC-ONLY (every differing byte is a rel32, RIP-relative or image-base
displacement that lands on the mapped counterpart of its target). Data: 35
XREF-EXACT, 7 XREF-BRACKET. The code moved by `-0x30` to `-0x120` (most
`-0xA0` or `-0x60`); .data by 0 for the light grid and Explorer Cam globals,
`-0x30` or `-0x40` for the vtables and name literals. A further 232 addresses
that the old inventory never listed were mapped the same way
(`.agents/build-334925/map_extra.json`): `mem_tick.cpp`'s 18 byte pins and 3
data globals (added after the 334473 retarget), the CPU profiler's class
tables, the rigs' layouts and the comment citations.

Not addresses, but build facts that moved with the file: the Oculus profile
floors `.text`'s span at `0x4DB4A00` (the 334473 value `0x4DB4C00` would have
refused 334925), two derived constants in `kinematic_eval_hook.cpp`
(`base + 0x43513A5`, the end of the list-merge hook site, and the part-test
return `0x42B77B6`), and the installer's qualified-SHA pin.

## What was verified against the 334925 executable

- **143 pins** (`.agents/build-334925/pins.py`): byte arrays, `{rva, n, bytes}`
  tables, the 11 Oculus fingerprints, 5 kinematic body hashes, the terrain
  cover's call-site chain. Before the edit pass 110 matched as written, 32
  changed only in rel32/RIP/disp32 fields (21 in C++ source, the 11 Python
  fingerprints in `tools/elite_oculus.py`), none were outside a displacement
  field. After it, all 142 byte and hash pins equal the 334925 bytes and the
  334473 executable reproduces the baseline (`pins_baseline.json`); the site
  chain is `SITE-OK` with the same fragment gaps.
- **`tools/elite_oculus.py` on the 334925 executable** accepts it (identity,
  IAT import, selector, call chain, the three relocated vtable pointers) and
  rejects 334473.
- **Data** (`.agents/build-334925/verify_data.py`): the four head-joint
  vtable slots of both skeleton classes, the Supersampling setter, getter and
  loader slots, the 8 flat stationary provider pairs, the 54-entry part-name
  table and the four joint-name literals all read as the source expects.
  Not-confirmed slots in the other 13 vtables are slots no EDVR code reads.
- **Every code-range hex literal in `src/`** (186 distinct): 185 have the same
  bytes (displacements masked) at the 334473 counterpart; the other is the
  `.text` floor above.
- The rigs and the build: `build.bat --wait-lock` green. Two rig assertions
  tied to the old addresses were corrected: Explorer Cam's 64-byte alignment
  claim for the avatar fade (`0x3DD8C60` is 32-byte aligned), and the UI panel
  rig's site-end virtual address.

## For the next retarget

Reuse `.agents/build-334925/`: `map_all.json` / `map_extra.json` carry the
334473 → 334925 map in the `map_all.json` format, `retarget.py` and `pins.py`
are ported to this arc (`pins.py --mode pre --write-baseline` before the edit
pass, `retarget.py --apply`, `pins.py --mode post --apply-new`, then `--mode
post` again), `verify_data.py` checks the data side. The branch retargeting the
on-foot addresses can map any 334473 (or 332841) address without rebuilding the
map; the caches sit in the main checkout's `analysis/`:

```text
python tools\build_diff.py map --old C:\Users\seanm\projects\edvr-unofficial-patch\analysis\EliteDangerous64-334473.exe ^
  --new C:\Users\seanm\projects\edvr-unofficial-patch\analysis\EliteDangerous64-334925.exe ^
  --cache C:\Users\seanm\projects\edvr-unofficial-patch\analysis\build_map_334473_to_334925.cache.json ^
  --rvas-file <one old RVA per line> --json <out.json>
```

`build_map_332841_to_334925.cache.json` is the direct 332841 → 334925 map for
addresses still in the first build's coordinates (`--old …\EliteDangerous64.exe`).
Run `python tools\build_diff.py capture` after the update, as this one did.
