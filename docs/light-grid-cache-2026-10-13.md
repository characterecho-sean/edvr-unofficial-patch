# Light grid cache (the fragment-culling cluster builder), 2026-10-13

## Status

- **State (2026-10-13): flown twice. Flight 1 (57f5393e): never engaged (template bug, fixed). Flight 2 (f8ecb500): the self-check turned the cache off at the first build. Flight 3 (9101d096) named the cause: the grid is CEIL(size / tile), the derivation used floor (fixed, NOT re-flown).** Branch `claude/light-grid-cache`, from the optimized-station merge on main (7e44b86c). Full `build.bat` green; the rig is `tools\light_grid_cache_test` (1073 checks; a 23-edit mutant sweep run by hand killed all 23). No key: always on, both profiles, a pure optimisation.
- **What it is.** A CodeHook on the entry of Frontier's cluster builder, `EliteDangerous64.exe` build 332841 (PE stamp 1788384820, size 104894464) RVA 0x58B150, one caller (0x590368), about 2.2 calls a frame at 0.285 ms a missed call (about 0.6 ms of render-thread CPU a frame). The game keeps a one-slot memo (8% hits). This keeps up to 20 states per context and swaps a kept state back in when a call's key matches bit for bit.
- **Why exact keys repeat (the probe's "17 distinct keys, every repeat gave the same table").** EDVR's jitter is a Halton (2,3) cycle of 8 frames (`native_temporal.cpp` `jitterCycleFor`: 8 for every engine but XeSS), the same offset for both eyes, so one context sees 2 eyes x 8 phases = 16 keys plus a third view. 20 slots a context hold them all: after warm-up the expected hit rate is above 90%.
- **The output is a STATE, not two tables (corrects the brief).** The build also fills a third vector (this+0x110, 48-byte elements, 58B8F5..58B94F) and replaces four refcounted GPU objects (this+0x130..0x148: two buffers and their views, 58BA2F..58BD57). A table-copying cache would leave the GPU buffers stale. So a slot holds a whole state (key 0x00..0x77, the vectors at 0x80, 0xA0, 0x110, the four pointers: 0xF8 bytes) and a hit SWAPS states: no copy, no allocation, no refcount, nobody frees what another holds. A miss first parks the context's old state in the LRU slot, then the game rebuilds in place. Empty slots start from an empty state MADE at first sight (key zero, vectors with capacity 0 and no data, no GPU object, each vector's own second header word kept), valid because the game's grow, release and GPU-release code all take null.
- **The key is the game's key plus one value.** The build's usual path is the OVERRIDE path (global byte 0x5E70F7E is 1 in the exe's data and no code writes it): it copies the view block (0x57A460), ORs 0xD into the copy's flags, sets near and far from the floats at 0x5E70F94/98 (1.0 and 10000.0), runs 0x4F2FF0 on the copy and keys on the copy's rows. The glue does the same on a local copy (pinned functions) before it decides. The loops re-read the view's own near (a4+0x234, 58B5E4), which the override path's key does not hold, so the slot also carries it. Tile 120 and slices 32 are the exe's data too (17 x 17 x 32 clusters is the measured 296,960 bytes).
- **Safety.** Identity (stamp, size) then three 16-byte pins (builder, 0x4F2FF0, 0x57A460); render thread only (other threads go to the game whole); every access SEH-guarded, a half-written swap is undone; forwarded whole when the context's first-call flag is set, a force-rebuild global is set, the inputs cannot be keyed, the renderer changed or rows cannot be derived. After EVERY game build the stored key is compared with the key the glue built (self-check: a difference turns the cache off). One cache hit in 64 (the first included) is not served: the game rebuilds and the three tables are compared byte for byte with the kept state; a difference turns the cache off for the session with a line saying why. Padding-lane-only differences (the unwritten 4th float of each half of a 32-byte element) are counted apart.
- **Temporary instruments (listed per AGENTS; remove or ship when the arc closes).** The hit verification (1 in 1024 since 2026-10-14, `kVerifyEvery` in `light_grid_cache_core.h`; it was 1 in 64 until several flights showed 0 mismatches) and the key self-check (kept as is). The verification can go altogether once more flights agree. The jitter probe (part 2): `jitter probe` and `jitter sample` lines. **No temporary key exists.**
- **Part 3 (jitter-tolerant reuse, key `light_grid_reuse_across_jitter`) was NOT built.** (1) It is unnecessary if the exact cache hits: the probe showed the keys repeat, and an exact hit has no shimmer risk by construction. (2) The jitter elements cannot be named with confidence from the code: the rows are the output of a mode-dependent transform (0x4F2FF0, selector at view+0x244) of a matrix at view+0x2B0 whose producer is not mapped; the inference "rows 0 and 2" rests on a 16-byte-chunk diff. The probe lines give the per-element answer in one flight. If the hit rate is low in a flight, the next step is that mask, not before.
- **Open hypotheses and their log signatures** (one flight reads them all). H1 keys repeat: `cache hits` above 90% of calls, `misses on a key evicted lately` near 0. H2 override path is live: `rows by the override path` about equal to calls. H3 templates made: `new context ... first seen with <flag, key, sizes, data, GPU>; empty template made` per context, `no template` 0. H4 exact: `verify N checks, 0 mismatches` (padding-only may be nonzero; say so). H5 key reading right: `key self-check M ok, 0 failed, 0 with the view block changing under the call`; if it fails, the OFF line names every differing field with both values. H6 GPU objects safe to hold across frames: no wrong light grid by eye (nothing in the log can see this; the verification compares tables, not GPU contents). H7 consumers re-read the context's pointers every call: same visual check. H8 the saving: `estimated saving` about 0.5 ms a frame; confirm in the frame-time line.
- **Ruled out (design).** A table-copying cache, because the state includes the 48-byte vector and four GPU objects (it would need the game's allocator and refcount release, and leave GPU buffers stale). Keying on the raw view block, because its first 0x40 bytes carry the head pose and change every frame. Calling the game's builder on a scratch context for verification, because every call would leak the scratch's vectors (rebuilding the real context from a spare slot needs none).

### 2026-10-13, flight 1: 0 hits (all four contexts "no template")

Log: `edvr_gfx_20261013_214308.log`, 19 min, 36 windows, eye 2016x2016, tile 120, 32 slices (the file defaults, as predicted), `rows by the override path` = calls (H2 confirmed). Detour installed at 21:43:08; the four contexts (two 2016x2016, one 256x256, one 612x248) were first seen at 21:43:46 and 21:43:51, each "already built". Every window: `no template` = calls, hits 0, misses 0, forwarded whole = calls, no jitter-probe lines.

Root cause (c8b0a068, `light_grid_cache_core.h` serve, line 584 then): the template was captured only when `(created || flag != 0) && statePristine(ctxState)` (`statePristine`, line 130: key all zero, vector sizes and data null, GPU pointers null). A context first met by the detour had the first-call flag clear (`first call` = 0 in every window, so the game's builder had never been seen with the flag set) and was not in the constructed state, so no template was ever taken and `if (!grp.haveTemplate)` forwarded every call. Which part of the state failed the test was not logged (the first-sight line said only "already built"); the contexts were therefore not constructed-and-untouched when the detour first saw them, whatever the load order was: the detour was in place 38 s before the first call, so the first call through it already found a flag-clear, non-empty state. The assumption "a context's first call arrives with the constructor's flag set and an empty state" was never established; it came from reading the builder, not the constructor.

Fix: the template is no longer captured, it is made (`makeEmptyTemplate`): key zero, every vector capacity 0, size 0, data null, GPU pointers null, and each vector's second header word copied from the context. Taking the template from the first forwarded build's resulting state is NOT equivalent (that state owns buffers, and a buffer in a slot and in the context at once is a double free); an empty state is the only template that is safe. Why the game accepts one: every grow path (0x598740, 0x5988F0, 0x598F10) reallocates through 0x55B720, which takes a null block (58B735 test rcx, je to a fresh allocation) with 0x53A590 behind it; the release 0x55B810 returns at once on null (55B813); the shrink path 0x598CC0 runs only when the size falls under half the capacity; the build tests each GPU pointer for null before releasing it (58BA42, 58BA7F, 58BABA, 58BAF6). The first-sight line now reports what was found (`first seen with first-call flag N, key set|zero, vector sizes a/b/c, vector data set|null x3, N GPU objects`), so the next log says what the constructor leaves.

Test (`testAlreadyBuilt`): a context built twice by the fake game, flag clear, key set, vectors and GPU objects present, hint words nonzero, then four such contexts at once; asserts the template exists, hits and misses (no forwarding), coherence, singly owned pointers, equality with a fresh build, the hint words kept, and the first-seen description. Mutants "template only when pristine", "template only on flag" and "template drops hint words" are killed.

### 2026-10-14, flight 3: the diagnostic named it, the grid is CEIL

Build 9101d096, 06:10:27: `OFF ... (grid x derived 16 stored 17; grid y derived 16 stored 17); a second derivation after the call gave the same key, so the view block did not move; after the build the vectors hold 9248/32/9248 elements; override path 1, extra near 0x3ccccccd`. 9248 = 17 x 17 x 32.

Root cause: I read the routine the build calls on the quotient (0x48AAAE8) as floorf and it is ceilf. The routine, instruction by instruction: 48AAAF1..48AAAFD split the bits into the magnitude and the sign (r8 = sign). 48AAB01: magnitude >= 0x4B800000 (2^23) is already integral, returned as is (NaN and infinity leave through 48AAB08). 48AAB16: below 1.0, zero returns itself, a negative gives -0.0 (48AAB26), a POSITIVE gives +1.0 (48AAB36 loads the float at 0x4DDE614, which is 1.0): that alone is a round-up, and a floor would give 0. 48AAB40..48AAB53: from 1.0 up the mantissa bits below the binary point are cleared (mask = 0xFFFFFFFF << (150 - exponent)). 48AAB5D..48AAB6E: a negative keeps the truncation; a positive keeps it only if nothing was cut (48AAB62 cmp edx, eax), otherwise adds 1.0 (48AAB66, again 0x4DDE614). I stopped reading at the truncation and took the last addss for a sign fix-up. Both axes use it (58B378 for the width, 58B3A0 for the height, the same call). So a width divisible by the tile stays (1920 / 120 = 16), anything else rounds up (2016 / 120 = 16.8 gives 17).

Fix: `gameCeilf` in the core is that routine; `gridCells` calls it. Tests: `testGridCeil` (2016/120 = 17, 1920/120 = 16, 1921 = 17, 2040 = 17, 2041 = 18, the flight's other sizes 256, 612, 248, the flat sizes 3840, 2560, 1080, 1, 120, 121; 2016x2016 at tile 120 and 32 slices is 9248 clusters; `gameCeilf` against an instruction-by-instruction transcription with the registers as variables, on every quotient of 15 tiles x 9000 sizes and 400000 bit patterns, bit for bit, and both against ceilf). Every earlier statement in this doc that the grid floors is wrong; the 296,960-byte tables of the first probe were always 17 x 17 x 32 + 32 elements.
